# 自动挥杆检测可行性(自研 AutoShot,2026-07-05)

> **一句话(经 Codex + Gemini 对抗评审后下调,2026-07-06):这是「值得受控验证的方向假设」,不是「可行性结论」。技术上能做,但离「低风险进产品」还很远。第一步不该是自动挥杆检测,而是「表盘一键记杆按钮 + 自动 GPS + 默认球杆」(100% 准、零误检、零耗电),外加静默影子采集;AutoShot 只有等真机真球场数据证明误报/漏报/续航都过线,才产品化。**
>
> **缘起**:复盘里的杆全来自 Garmin 设备(它会漏记短打/推杆、错记练习挥)。与其把「手动改杆」做很重去兜 Garmin 的不准,不如自己在上游把挥杆检测做准。检测准了,手动修正的需求自然就降。对齐 R12 方向 [[auto-shot-tracking-vision]]。这份是让强模型(Fable 独立查证)深挖的初稿;**2026-07-06 又经 Codex(gpt-5.5-xhigh)+ Gemini(3.1-pro)独立对抗评审、大幅下调乐观度**——两家收敛结论见文末「评审记录」,正文已按评审更正。

## 1. 结论先说(人话)

- **能不能做到?能。** 已有量产先例:**Golfshot** 早在 Apple Watch Series 3 / watchOS 7 上就用机器学习做到了全自动记杆,连推杆都检测(只是不测推杆距离)。这说明普通 100Hz 传感器就够做出可用的挥杆检测,不是高门槛黑科技。
- **Apple 还给了更好的工具。** watchOS 10 起有专门的高频传感器接口(800Hz 加速度计),苹果自己在 WWDC23 演讲里**把 golf 列为目标运动之一**,还讲了整套「怎么从传感器信号里定位到击球那一下」的算法(**注意:演讲现场演示的是棒球,不是高尔夫——评审提醒棒球双手握、更重、空中击打无草皮反震,受力波形和单手腕上的高尔夫完全不同,不能照搬,只能借思路**)。
- **真正的难点不是「检测挥杆」,是分清短打/推杆和练习挥。** 全挥杆很好认(击球那下的高频震动信号最明显);难的是:① 推杆/切杆这种小动作,腕上传感器接近测不准(Garmin 干脆放弃、靠杆端外置传感器 CT10 补);② 练习挥、擦地空挥容易被误记成一杆。
- **而这两个难点,恰好是我们已有的数据能补的**(见 §4)。所以结论是:**别追求纯自动,做「自动检测 + 每洞确认」的混合**——把「漏记/错记」从「数据脏、要手动大改」变成「洞末点一下」,还顺带产出训练数据。

## 2. Garmin AutoShot 是怎么做的(照抄它的机制)

- **机制**:靠**加速度计 + 陀螺仪**,结合你设置的**佩戴手腕**,认「上杆动作 + 杆面击球的冲击」——**只认全挥杆**。GPS 不负责检测,只负责标**击球位置**;距离是走到下一杆位置时,用前后两个击球点的位移算出来的。
- **它明说不检测的**:推杆、切杆、半挥、救球杆(官方手册原文「推杆不被检测」)。这些要靠杆端传感器 CT10 补。
- **已知会误记**:球车旁边的练习挥、球车颠簸的震动,都可能被记成一杆;用户得事后在 Garmin app 里手动改。
- **所以**:我们复盘里看到的「漏记 + 错记」**不是 Garmin 没做好,是腕上传感器的固有形态**。我们自研也会撞同一堵墙——这正是要靠数据融合(§4)+ 用户确认来翻墙,而不是幻想纯自动能测准推杆。

> **负责人观察(2026-07-06)+ 关键更正:试挥 vs 真打靠「抓冲击」,不是靠「抓位置」。**
> 实测 Garmin:你试挥半天没打、往前走,它**不记**这一杆。说明它**不是**「同一小片位置挥好几下取最后一杆」那种位置聚类——真那样试挥走开就该误记了。**它抓的是击球那一下的冲击本身;没真打到球,就没有「一杆」这个事件。**
> - **为什么冲击是唯一可靠的判据**:挥杆动作本身,试挥和真打**几乎一模一样**(试挥就是在模拟真打)——靠「动作形态」分不出来。唯一可靠的区别就是**有没有真打到球**:① 触球一瞬间有一记**又短又猛的高频冲击**(几毫秒,顺杆身传到手腕),空挥穿过空气没有;② 触球那下**能量被球带走、杆头突然减速**,空挥是顺滑收住。这两样空挥都没有。
> - **这也是要上 800Hz 的理由**:冲击是毫秒级事件,100Hz 可能抹平,800Hz 才能干净分离(WWDC 的棒球例子正是用高频找击球「回震」)。
> - **难的那 10%**:干净空挥(不碰地)最好分;**擦地/打垫子的试挥也产生一记冲击**,腕上不易和真打分开——这就是 Garmin 偶尔误记的那种(用力练习挥、球车颠簸同理)。
>
> **⚠ 评审再更正(2026-07-06,Codex + Gemini 双家一致否掉「冲击=主判据」的说法):**
> - **物理上「冲击=主判据」站不住,而且反直觉**:表在**手腕不在杆头**,冲击经手、握把、手套、表带、软组织层层衰减。**试挥擦地/砸草皮(divot)在腕上的冲击,往往比你干净扫球(pick clean)还猛**;反过来**薄击、沙坑(打的是沙)、软切、推杆这些真打的冲击极弱**。所以「光靠冲击」→ 海量试挥误检 + 短打真打漏检。**空挥好分,是因为它没冲击;但「有冲击」远不等于「真打」。**
> - **正确的判据 = 行为状态机 + 概率融合,不是单一冲击**:准备静止 → 一段疑似挥杆运动 + 冲击特征 → 之后走向下一个点(play 状态推进)。冲击只是其中**一个强特征**,不是地基。这也和负责人的观察自洽:Garmin 没记你的空挥,是「弱冲击 + play 没推进」一起判的结果,不是「只看位置」也不是「只看冲击」。(Codex 补:Golfshot 官方说明里「练习挥先被记、真打后替换」恰恰说明**位置/后续状态机很重要**。)
> - **GPS / 几何 / 记分**因此**不是「冲击的兜底」,而是状态机里同等重要的上下文信号**(见 §4,但注意它们在短打上基本失效)。

## 3. Apple Watch 能做到什么

- **高频传感器**:`CMBatchedSensorManager`(watchOS 10+)能到 800Hz 加速度计 + 200Hz 姿态(普通接口只有 100Hz),按每秒一批交付。需要挂一个**活跃的健身 workout**(golf 类型)才能拿数据。
- **设备门槛**:苹果 2023 年说 Series 8 / Ultra 支持高频采样;更新的 S9/S10/Ultra 2 应该也支持(**这是合理推测,没找到官方明文列表**)——代码里运行时判断「是否支持」即可,老表退回 100Hz。
- **续航**:参照 Golfshot 官方口径,自动记杆一场大约耗 **25%–55% 电量**(含 workout + GPS + 传感器),可接受。800Hz 本身的额外功耗**苹果没公布(未知项)**;缓解办法是平时用低频「疑似挥杆」门控、只在候选窗口里才取高频。
- **表上跑模型**:Core ML 在表上原生可用,苹果的 Create ML 有现成的「动作分类」模板(输入就是传感器序列),适合把「挥杆 vs 非挥杆」分类器直接放表上跑。

## 4. 我们已有的数据能补什么(关键——这是我们比 Garmin 强的地方)

行业(Arccos)已验证的模式就是「传感器报击球 + GPS 记坐标 + 用前后两点算距离」。我们手里的四样东西能搭出同款、甚至更强的**仲裁器**:

- **GPS 位移(已有 GPS 流)= 兜底裁判,不是主防练习挥**(练习挥主要靠「无冲击」在上游就滤掉,见 §2 更正)。它处理的是**冲击判据也分不清的残留情形**——比如擦地试挥误触发了一记冲击:若这个疑似击球**之后人没往前走、下一杆也不在新位置**,就把它降权/丢弃;真打完人会走到球旁打下一杆。局限:短切/推杆位移太小,淹在 GPS 噪声里(消费级手表距离误差约 3%–6%)——所以 GPS 只能仲裁全挥杆。
- **球洞几何(已有 CourseView 精确果岭/障碍/发球台多边形)**:在发球台 → 大概率开球杆;进了果岭多边形 → 切「推杆模式」(只数不测距,学 Golfshot);球道中段静止一会儿 + 有击球冲击 → 更可能真打。**只是软先验,不是硬判据**:评审提醒 —— 发球台上可能别人开球你在旁试挥;国内球场临近洞多、发球台/隔壁球道挨得近 + GPS 漂移 → 几何判定直接失效;旧球场数据、fringe/错洞也会坑。(原稿「Garmin 没把几何用到这个深度」无证据,已删。)
- **自测球杆距离(已有)**:某杆的 GPS 位移和所选球杆的距离分布对不上(7 铁打出 250 码)→ **只标可疑、提示用户,绝不自动写入**(守「不造假」;评审:非标准杆很常见——7 铁林中轻敲救球 30 码,距离倒推球杆毫无意义)。而且球杆距离分布本身还被 Garmin 的漏记/错记污染,是脏数据。
- **记分数据(已有实时记分,含推杆数)= 弱监督,不是每杆真值**:每洞结束,拿「用户报的杆数」对「自动检测到的杆数」对账 → 差多少,**量化**了这一洞的漏检/误检,是**给用户的一键修正入口**。但评审点破:记分只给**每洞总数**,不给每一杆的时间戳/球杆/真假对应,还被罚杆/让杆(gimme)/拾球/暂定球污染 → **不能当每杆标注直接训模型**,只能做弱监督。~~「免费训练标注」的说法已收回。~~

## 5. 精度能到哪(诚实版,别夸)

- **难度排序**:全挥杆(容易)>> 切杆/半挥(难)> 推杆(腕上单传感器接近不可靠)。
- **有几分证据**:网球类比研究里大动作 94%–98%、小动作(截击)只有 23%–44%——**大动作好检、小动作难检**这条规律很稳(但该研究传感器戴在背部不是手腕,类比要打折)。~~学术上击球瞬间检出 99%~~ —— **评审(两家一致)判定此条无参考价值、已删**:那是**视频重建的合成数据**给腕上 IMU 背书(Gemini:「苹果比坦克」),不能拿来壮胆。
- **没有公开的、真手表上的「击球检测准确率」黄金数字**——Garmin / Golfshot / Arccos 都不公布。**谁做谁自己测**,所以下面阶段计划第一件事就是攒我们自己的标注集。
- **预期(推测)**:全挥杆检出 90% 后段–95%+ 可期,误报能靠 GPS 门控压很低;切杆/半挥明显差;**腕上推杆检测别指望自动可靠**(Garmin 用外置传感器,Golfshot 只敢数不敢测距)。

## 6. 分阶段建议(经评审重排 —— 手动优先,自动检测无限后置到数据过线)

> **评审两家一致砸掉了原「阶段1 = 震动一键确认」**:100Hz 规则式误检率高得离谱(球车颠簸、大力试挥都触发),在你 pre-shot routine 时震一下问「打了吗」会激怒球手、一场震上百次、第三洞就被关掉;而且 `CMBatchedSensorManager` 是**批量延迟**交付,**根本拿不到实时击球瞬间去震动**——接口层面就否了。所以顺序改成:

- **阶段 -1(先做这个,零算法、零误检、100% 准)**:**表盘常驻「一键记杆」大按钮** —— 击球前/后瞄一眼表点一下,记当前 GPS + 时间戳,默认填推荐球杆。这直接拿到我们真正想要的**击球位置 + 球杆**,零耗电、零打扰。**连这个交互都没跑通,别碰 IMU 自动检测。**(两家一致:这才是第一步。)
- **阶段 0(纯现有栈)**:实时球局每次记杆打 GPS 戳(网页 RecordRoundPage 已这么做),把「前后两点位移 = 杆距」跑通,攒位置流基线。
- **阶段 0.5(硬门槛,写任何检测逻辑之前必须过)**:**真机戴表 5 小时实测** —— 开 golf workout + 800Hz batched 采样 + 跑空 Core ML 模型,模拟球场走动/停顿,看**发不发烫、电量崩不崩、进程会不会被 watchOS 挂起/杀掉**。过不了这关,后面免谈。
- **阶段 1(静默影子模式,不打扰用户)**:Watch 起 golf workout 后台采 IMU + GPS,**绝不在击球瞬间震动/弹窗**;用户手动记分(阶段 -1)当**真值**,后台悄悄记「疑似挥杆候选」,**洞末或手机端**轻量复核对账。这才是安全的攒数据方式——而且能同时攒到**正样本和负样本**(评审:只记「确认过的」= 只有正样本,模型训不出来)。
- **阶段 2(提准,需真数据先过线)**:用影子模式 + 自采标注(见下)训练 Core ML「挥杆 vs 非挥杆」分类器 = **行为状态机 + 冲击特征 + 上下文**的概率系统(不是单看冲击);Series 8+ 叠 800Hz 只作为**待测增益项**(连续高频 / 预触发 / 纯 100Hz 三组真机对比电量与收益);果岭内推杆只计数 + 和记分推杆数对账。
- **阶段 3(才谈提示体验)**:**只有实测达标**(比如每轮误提示 < 3–5 次、全挥漏检 < 10%、电量可控)才开自动提示;高置信免确认、低置信才问;和 Garmin 导入数据互补合并。

> **冷启动数据现实(评审重锤)**:靠「阶段 1 顺便攒训练集」是幻想 —— 一两周只能做埋点原型,攒不出覆盖设备/手腕/球场/球杆/短打/推杆/球车/练习场的可用数据集,而且缺负样本。**要认真做,得公司自己出钱派人戴表去练习场/球场、高速摄像同步时间戳、人肉打标几千次(含各种异常动作)**,别指望半成品吸用户的血白嫖。这是一笔明确的、不小的前期投入。

## 7. 和复盘 v2 的关系

- 自动检测 = **上游**把数据做准;复盘 v2 的手动增/改/删杆 = **下游**兜底。两者互补不冲突。
- 复盘 v2 的修正层已经是 op-based 事件日志,**天然给 AutoShot 留了位**:AutoShot 只当「新来源、只出建议、永不覆盖手动」,冲突进待处理队列。所以先做哪个都不堵另一个。
- **门控**:这是产品**方向**研究,不是要马上开工。真要动手,从阶段 0/1 起(纯软件、低风险),等负责人点头。

4. **数据融合四件套是弱约束、补不了短打**:GPS 3-6m 淹没果岭边短打;几何在临近洞/漂移/旧数据失效;球杆距离倒推非标准杆无意义、数据本身脏。降级为软置信度(§4 已更正)。
5. **冷启动数据是假闭环**:记分不是每杆标注;只记「确认过的」= 只有正样本、无负样本 → 模型训不出。要**公司自费真人真机+高速摄像同步打标几千次**(§6 已加)。
6. **作为 Garmin 备份 ROI 低,有更聪明平替**:重度 Garmin 用户不会同时戴 Apple Watch。**第一步直接做「一键记杆按钮 + 自动GPS + 默认球杆」**(100%准/零误检/零耗电/零算法),AutoShot 不该是近期主线(§6 阶段-1 + 门控已加)。

**Gemini 独抓、原稿全漏的必补 caveat:**
- **左撇子 / 手表戴哪只手**:戴左手(引导臂)vs 右手(跟随臂)加速度/陀螺曲线**镜像且波形不同**;模型不区分佩戴手 + 惯用手 → 直接废。**任何检测方案的第一性输入。**
- **老表被系统性放弃**:若核心架构靠 800Hz 区分试挥,而 S7/SE 只有 100Hz「退回」,等于放弃大量老用户,不是优雅降级。→ 检测逻辑不能硬依赖 800Hz。

**Codex 独抓:**
- **隐私 / HealthKit / App Store**:Motion&Fitness + GPS + 训练数据属敏感域,Apple 指南限制健康数据用于挖掘、要求披露、禁写假健康数据。→ **传感器训练数据单独 opt-in、不默认上传;未确认的推断绝不写进正式统计。**
- **别从一次观察反推机制**:Garmin S20 手册只确认「记录击球位置 / 需开记分 / 好接触更好 / 推杆不检测」,没公开证明算法就是「上杆+冲击」;「不检测切杆/半挥」应写成「可能不稳定 / 部分设备不支持」,别当全设备官方事实。

**结论**:方向不砍,但**降格为「受控验证假设」**;近期主线转向「手动一键记杆 + 影子采集 + 真机续航实测」,AutoShot 产品化等真实 18 洞数据把误报/漏报/续航都证明过线。**待负责人拍板优先级。**
