# 「打开即用」设计:数据一进来就自动备好,打开就秒看(2026-07-07)

> **一句话**:不管是统计、最近一盘、还是别的,它们的准备工作都在**后台自动做好、缓存好**,你一打开应用第一屏就是现成的——对标 Garmin 的流畅。核心不是"把文件变小",是**合理安排"什么时候、在哪儿把东西备好"**。
>
> **缘起(负责人点破的关键)**:Garmin 快,是因为**数据一上传,它那头有个触发器、自动就去算/备好**。咱们现在只有半个——定时同步拉到新球局后,**只重新烤了"统计"缓存,没去准备"最近一盘"那套东西**(那盘的球洞图、逐杆过程,现在是你点进去才现渲、要等 6–10 秒)。这份设计补上那个触发器,并把"备什么"讲清楚。

## 1. 先定的两件事

- **A 模式(Garmin 那样)**:打开**立刻显示"上次算好的"**,同时**后台悄悄刷新**。永远瞬开,代价是偶尔看到的是稍旧的数(几秒后自动变最新)。负责人拍板选 A。统计尤其适合 A——差一两盘无所谓。
- **默认全自动,不用你伺候系统**:准备工作挂在"自动同步"后面自动触发;另给一个**可选**的"拉一下最新"按钮,只在你等不及时用。

## 2. 数据怎么来 + 触发器挂在哪(核心)

**先说清楚一个现实**:高尔夫数据只有一条路——**咱们去 Garmin 那儿"拉"**(Garmin 不会主动推给咱们,见 [[garmin-auth-reality]])。所以"这盘什么时候进咱们系统"= **咱们多久拉一次**。Garmin 自己即时,是因为你就打在 Garmin 表上、直接进它自己的云。

**触发器 = 挂在"新数据落地"那一下,自动触发一步「准备最近一盘」。** 三个自动触发点 + 一个手动:
1. **定时自动同步**(现有 `ops/auto_sync.sh`)——拉到新球局 → 落地即触发准备。**把频率从"一天两次"提到"每小时一次"**:平时只是轻量增量拉(便宜),只有 cookie 过期才需要那次较重的自愈,所以提频可行。这样你打完**个把小时内**自动就能看。
2. **手动记分**(手机 GPS 记分 RecordRoundPage)——本就是即时落地,顺带触发准备。
3. **服务器启动**——现有 `warm_stats_cache` 已在启动烤统计;扩成也备好最近一盘。
4. **手动「拉一下最新」按钮**(可选)——哪天刚打完就想马上看,点一下:立刻拉 + 立刻备好。**平时不用碰。**

> 所以回答"我还得手动点你这边一下吗?"——**不用**。默认全自动(每小时);那个按钮只是给你个"我等不及了"的开关。

## 3. 「准备最近一盘」到底备什么

新数据一落地,后台这一步(一个可复用的活)把这盘要用的整套备好、缓存:
1. **烤统计缓存**(已有 `stats_cache`,按文件指纹失效/重算)。
2. **把这盘球场每个洞的球洞图提前渲好缓存**——复用现有的球洞图预渲(`POST …/topo/prewarm` + 磁盘缓存)。现在它是"开局才调 / 点进课程才调";**改成"数据一落地就替这盘的球场调一次"**。这是最贵的一块(渲染),备好了后面全省。
3. **把这盘的逐杆复盘数据(每洞落点图)算好**——落点图的贵处就是球洞图渲染(第 2 步已备);**确认落点图接口用的是"备好的那张缓存图"**(实现时要核:`build_round_hole_shot_map` 走的渲染要命中第 2 步的缓存,否则白备)。
4. **刷新首页"最近一盘"卡 + 概览**(现有 `/history/summary` 从缓存切,轻量)。

## 4. 不重复瞎算

- 统计:文件指纹没变就秒回缓存(已有)。
- 球洞图:磁盘缓存 + 版本号(已有;改样式才 bump)。
- **给"这盘备好了没"加个小标记**:准备这一步先看"这盘的球场+版本是不是已经备过",备过直接跳过。所以每小时触发也不会反复重渲同一盘。
- 只准备**最近的这一盘(或最近少数几盘)**,不是全量重算历史。

## 5. 你会看到什么

- **首页"最近一盘"卡**:上一场是什么(球场 / 日期 / 成绩)+ **一张真实球道预览图**(就是第 3 步第 2 项提前渲好的那张,不是占位方块)。
- **点进去**:逐洞、逐杆过程(落点图 + 每杆什么杆打多远)**秒开**,因为全提前备好了。
- 全程 **A 模式**:先给缓存的、后台悄悄刷新成最新。
- 补充现状:首页大概已有"上一场"卡,但**(a)预览是不是真实球道、(b)点进去是不是秒开**——靠这套触发器补齐,不是从零做。

## 6. 复用什么 / 新做什么

**复用(地基已在)**:`stats_cache`(指纹缓存+启动烤+记分后重烤)、球洞图预渲+磁盘缓存、`POST …/topo/prewarm`、`/history/summary` 轻量首屏、`auto_sync.sh` 定时同步。

**新做**:
- 一个可复用的后端活「准备最近一盘」= 烤统计 + 替这盘球场预渲球洞图 + 备好逐杆复盘 + 刷新首页卡;带"备过就跳过"的标记。
- 把它挂到三个自动触发点(同步尾巴 / 记分落地 / 启动)+ 一个手动端点(给「拉一下最新」按钮)。
- `auto_sync.sh` 频率:一天两次 → 每小时。
- 首页"最近一盘"卡接**真实球道预览图** + 保证点进去秒开(iOS + 网页)。

## 7. MVP 边界

**进 MVP**:触发器(挂同步尾巴 + 记分 + 启动)· 「准备最近一盘」备好统计+这盘球洞图+逐杆复盘 · 每小时同步 · 首页卡真实预览 + 秒开 · A 模式(先缓存后刷新)。

**后置 / 可选**:「拉一下最新」手动按钮(锦上添花,不是必须)· 预备"最近几盘"而不只最近一盘 · 更细的后台刷新提示("正在更新…")。

## 8. 要在做计划时核实的点(诚实留白)

- **落点图渲染是否真命中球洞图缓存**(§3 第 3 项)——若 `build_round_hole_shot_map` 用的是另一条没缓存的渲染,得先接上,否则"备好了"是假的。
- **每小时同步的真实成本**:cookie 自愈多久触发一次、增量拉多重——若比预期贵,退回"每 2–3 小时"或"只在白天时段每小时"。
- **触发器怎么知道"哪盘是新的"**:同步落地后按最新 scorecard 判定,只备新的那盘。
- **多用户**:每个成员各自的最近一盘各自备(按 [[multi-user-redesign]] 的 per-player 隔离)。
